# lint

The lint module gives a campaign a repeatable health check for its wiki: a deterministic reporter, `eddic_lint.py`, that walks a tree of interlinked markdown pages and names the structural rot it finds. It is the reporter half of a reporter/model seam. The script never edits anything — it emits findings; deciding which to fix and which to escalate is the agent's half. That division is deliberate and load-bearing: judgment stays with the agent and the owner, while the machine-checkable floor stays deterministic and stdlib-only, runnable on any Python 3.9+ via `uv run` with nothing to install. This is the [deterministic core](../concepts/deterministic-core.md) applied to wiki maintenance.

## Invocation and exit codes

The reporter takes a wiki directory and optional flags: `uv run scripts/eddic_lint.py <wiki_dir> [--json] [--strict] [--show-quieted] [--log NAME] [--contribs DIR]`. It exits `0` when clean, `1` when there are errors, and `2` on a usage problem such as a missing directory. Info-level findings never fail a run. Warnings fail only under `--strict`, the mode routines and CI use, where an unread warning is a warning that never gets fixed. `--json` emits the machine-readable report for a consuming agent instead of the human-readable table. When run as a vendored `eddic` verb with `EDDIC_CONFIG` set, it takes the wiki, log name, and contribs directory from the campaign config.

## Severity tiers

Every finding carries a severity that determines whether it fails the run. Errors are broken links and anchors, missing titles, site-rooted links, malformed log entries, firewall breaches, the contributor-overlay and transaction-arc structural faults, and the pen-axis and merge-marker faults. Warnings are stub drift, orphans, and unreachable pages — graph-connectivity problems that are real but not build-breaking outside strict mode. Info covers tiny unstubbed pages, open merge proposals, and the firewall-skipped notice; these are signals, not failures.

## Advisory and binding checks

Severity decides whether a finding fails the run; a second, orthogonal split decides whether it is reported at all. Four checks are advisory — `stub-overgrown`, `tiny-unstubbed`, `orphan`, and `unreachable` — editorial nagging about page shape rather than defects a build trips over. They go quiet on a page that says the pen is held elsewhere: `curation: human`, the owner's `lint: off` opt-out, or an open merge proposal. Nagging a human about the page they are answerable for is noise, and holding a transient proposal to canon's standards is nonsense. Every other check is binding and never quiets, on any page, for any marker — the firewall, the rights and attribution machinery, and the structural integrity a build depends on. The advisory set is a closed enumeration, so a check added later is binding unless it is deliberately marked advisory; the tier fails closed the way the visibility axis does. Quieting is not silence: the summary always counts what it suppressed, `--show-quieted` lists it with each such finding flagged, and neither the count nor the listing moves the exit code. An owner who opts out of advice has not opted out of the safety net, and advisory findings that vanish unexpectedly are a marker to read before they are a bug to chase.

## Structure checks

Each page is parsed with its frontmatter split off and fenced or inline code stripped before analysis. A page with no line beginning `# ` raises `missing-h1` (error) — every page needs a title. Word count is measured on body prose only. A page whose last non-empty line is exactly `STUB` is a stub; if a stub grows past 150 words it raises `stub-overgrown` (warning), a prompt to promote it. A non-stub page under 30 words raises `tiny-unstubbed` (info), flagging an underweight page.

## Link and anchor resolution

Markdown links `[text](target)` are extracted; image links are ignored. A target matching an external scheme (`https:`, `mailto:`, and the like) is skipped. A target beginning `/` is a site-rooted path that resolves on no Eddic surface and raises `absolute-link` (error). Otherwise the target is split on `#` into a path and a fragment. A path that names a wiki page is judged as one, whatever form it wears: a direct `.md`/`.MD` link, the page's rendered `.html`/`.htm` form, or a clean/extensionless URL (including a `.dm` twin's clean URL). The resolver maps each to the `.md` page it denotes, resolved relative to the directory of the page that contains the link. A direct `.md` link is *strict*: a path resolving outside the wiki root, or to a page that does not exist, raises `broken-link` (error). The rendered and clean-URL forms are *lenient*: they are judged only when their `.md` page actually exists, so a real asset (`foo.webp`, `foo.png`, …) and any other non-page target resolve to nothing and are neither errored nor counted as links — the same silence a non-`.md` link always got. This is what closes the firewall gap where a DM page linked as `.html` or a clean URL slipped past the `.md`-only check (issue #22). When a fragment is present, it is GitHub-slugified — lowercased, stripped of everything but word characters, dashes, and spaces, spaces to dashes — and must equal the slug of some heading in the destination (or, for a same-page `#anchor`, the current page), else `broken-anchor` (error).

## The firewall

The firewall check enforces that a player-visible page never links a hidden one. It fails closed: a page counts as DM-only unless its frontmatter says `visibility: player`. The check activates only when at least one page in the wiki carries `visibility` frontmatter. When it does, every player-visible page is examined, and any link from it to a non-player page raises `firewall-breach` (error). When no page anywhere carries visibility frontmatter, the whole check is skipped and a single `firewall-skipped` (info) finding is recorded — introducing visibility is the [wiki](wiki.md) module's job, not the linter's. See [the firewall](../concepts/the-firewall.md) and [projection and visibility](../concepts/projection-and-visibility.md) for the safety property this defends.

## Reachability and orphans

Both checks run over resolved page-to-page links — every link form that denotes a wiki page, resolved to its `.md`. The root catalogs are `index.md` and, where a DM catalog exists, `index.dm.md`; a player catalog can never link DM pages, so DM pages are reachable legitimately only via the DM catalog. A page not reached by following links from the roots raises `unreachable` (warning). A page with zero inbound links from any other page, and which is not itself a root, raises `orphan` (warning). Root catalogs are exempt from the orphan check.

## Operation log

The append-only operation log (default `log.md`, overridable with `--log`) is validated line by line: only lines beginning `## ` are checked. Each must match `## [YYYY-MM-DD] <type> | <summary>` — a two-hash prefix, a bracketed ISO date, a single whitespace-free type token, a space-pipe-space, and free-text summary. The type must be one of `ingest`, `reconcile`, `lint`, `schema`, `witness`, `attribution`, `consent`, or `sever`; any other value, or any malformed `## ` line, raises `log-malformed` (error). The linter never rewrites the log — a malformed entry is reported for the owner to decide on.

## Contributor overlays and transaction arcs

Given a `--contribs` directory, each contributor's files overlay the base wiki at their relative path or a declared `replaces:` target, and the lint sees the same effective view a build would. Structural faults are errors: two overlays claiming one target (`contrib-conflict`), an overlay landing on an existing base page without declaring `replaces:` (`contrib-collision`), a `replaces:` naming no base page (`contrib-replaces-missing`), and a file whose `authorship:` is missing or merely generic (`contrib-unattributed`) — attribution being the point of an overlay. Frontmatter for transaction arcs is validated too: a `transactability:` outside `transactable`, `transactable-with-attribution`, `local-only` raises `invalid-transactability`, and a `derived-from:` naming no page in the effective wiki raises `derived-from-missing`. See [contribs](contribs.md) for how overlays are authored.

## The pen axis and merge proposals

The three markers that say who writes a page next are checked for membership, and the check is binding — a page may not use a marker to silence the check policing its markers. A `curation:` outside `human` and `agent` raises `invalid-curation` (error), an `ingest:` outside `literal` and `derived` raises `invalid-ingest`, and a `lint:` outside `off` raises `invalid-lint`. Absence carries meaning in each case rather than being an omission to repair: no `curation:` marker means `agent`, and curation is asserted by the owner, never inferred from a page's authorship.

A page carrying `proposes-merge-into:` is a transient proposal awaiting the DM's adjudication. A target that names no page in the effective wiki raises `merge-target-missing` (error), and a proposal marked `visibility: player` raises `merge-proposal-visible` (error), because unadjudicated lore may not claim the player surface. Every open proposal also raises `merge-pending`, which is info severity and so never fails a run, and which is deliberately not advisory: open proposals are the DM's work queue, so they stay visible even on a page whose advisory findings have gone quiet. See [wiki](wiki.md) for the merge flow these markers belong to.

## Triage seam

The reporter stops at naming defects. Mechanical, art-free, reversible fixes — repointing a moved link, adding an implied title, weaving in an orphan, appending a `STUB` marker — an agent may make unasked. Anything touching visibility, promoting a stub, rewriting log history, altering human-authored prose, or settling a pen or merge marker is escalated to the owner: an out-of-set `curation:` value is usually a near-miss for something the owner meant, and a proposal claiming the player surface is fixed either by merging the lore or by hiding it, so both are questions about who holds the pen that guessing would answer wrongly. Every lint pass should close with a `lint` entry in the operation log recording what was found, fixed, and escalated. Within a maintenance cadence this runs inside every [routines](routines.md) pass.

## The semantic pass

The reporter/model seam has a second, model-run half, added at version 0.4.0: a semantic pass over what regex cannot see. A page can leak a spoiler in prose without linking a DM-only page; two pages can contradict each other while every link resolves; a name can drift across spellings that a mechanical rename never unified. `semantic_review.py` is the deterministic scaffolding around that judgment — it makes no judgments itself. Given a wiki directory and, separately, the built player projection, it assembles a review packet: the master pages, the projection pages kept apart, the semantic checklist, and the pinned findings schema. The packet is a pure function of the tree, so a run is reproducible and the setup is testable even though the reading is not.

The checklist names six things a careful maintainer catches by reading, each scoped to complement rather than repeat a structural check. `firewall-prose` is DM-adjacent knowledge in player-visible prose — read on the projection, never the master, because it judges what players actually see, and distinct from the structural `firewall-breach` which only follows links. `tonal-drift` is a page sliding out of the encyclopedia register. `contradiction` is a fact one page asserts and another denies. `dangling-reference` is a person, place, or event named as if known but established nowhere — prose with nothing behind it, which is not a broken link because no link exists. `naming-inconsistency` is one entity written more than one way. `stub-overgrown-prose` is a page that reads finished while still marked `STUB` below the word threshold `stub-overgrown` fires at. The packet also carries a `not_in_scope` list of the deterministic codes the floor already guarantees, so the pass never re-litigates them — the no-egg-sucking rule applied to the seam itself.

Findings are emitted as a JSON array against the schema `{page, anchor_or_line, category, severity, finding, suggested_fix}`, and `semantic_review.py --validate` enforces that schema before anything is filed. Delivery has two paths: a plain report folded into the `lint` log entry, or — when the [retrieval](retrieval.md) witness write path is enabled — one `suggest_edit` per finding into the DM's review inbox, materialized with `eddic suggestions` and disposed by hand. Both paths are advisory by construction: findings are suggestions, never applied edits; no human-authored prose is rewritten; the agent proposes and the human disposes. Because the pass is token-heavy it is off by default and, under a maintenance cadence, runs as its own between-sessions [routine](routines.md) rather than inside every freshness loop. See [the firewall](../concepts/the-firewall.md) for the safety property the firewall-prose check defends by judgment where the structural check defends by construction.
